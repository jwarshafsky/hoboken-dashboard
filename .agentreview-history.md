# /agentreview history — Commute app

One entry per round. This file is the "do NOT re-report" input for future
rounds; keep entries terse. The point is to vary the lens each time, not to
relive past reviews.

## Round 1 — 2026-07-30

**Agents:** performance + reliability engineer, QA / failure-modes reviewer,
on-the-move UX reviewer.

**Scope:** whole chain — app source, the launcher's Caddy `/commute/*` route,
the launcher shell, and the Cloud Run proxy path.

**Top findings (this round):**
- [shipped] Launcher posts `{type:'hidden'}` when the tile is swapped out, but the
  page only handled `'shown'` — `document.hidden` follows the TOP-level document
  inside the iframe, so the 15s poll ran forever on the launcher home screen.
  Measured 3 requests per 40s hidden before, 0 after. — perf agent
- [shipped] No fetch path checked `res.ok`. A 5xx with a JSON body rendered as a
  healthy, empty outbound board reading "none soon" — the app asserting no buses
  were coming when it had simply not been told. Fixed in `fetchT` so both
  directions use the error handling they already had. — QA agent
- [shipped] Service worker `activate` deleted every cache on the origin, not just
  its own. Caches are per-origin and on the launcher this SW shares the origin
  with every other tile. Filtered to the `commute-shell-` prefix. — perf agent
- [REJECTED] Serving the app from local disk instead of proxying to GitHub Pages.
  Jeff pre-approved this conditionally; it failed its own gate. Measured gain was
  ~55ms typical / ~103ms worst case, against a ~4.9s cold Cloud Run fetch — about
  2% of a cold open, in exchange for a second copy to keep in sync. The Caddyfile
  comment documenting the original decision was correct and stands. Note the
  premise that prompted this (a 475ms cold proxy hop) was a measurement artifact:
  n=80 real opens from the Caddy access log are p50 61ms / p90 177ms, and 475ms
  was the single worst sample.
- [shipped, after approval] Prewarm the Cloud Run cache on commute-tile touchstart
  (~4.4-4.9s → ~0.1s off-window). Jeff asked it not cost anything during the
  commute, so it is gated to fire ONLY off-window — inside the window the
  launcher's commute card already polls every 30s and keeps it warm. Net-zero
  during the commute, net-negative overall against the poll fix above.
- [shipped, after approval] Backoff 15s→60s on repeated failure. Capped at 60s
  rather than the usual 120s: for a bus board, slow recovery is worse than the
  requests saved.
- [shipped, after approval — CONFLICT RESOLVED] Staleness. QA wanted the dim
  treatment applied EARLIER (on the pocket-to-platform path a 10-minute-old
  countdown showed at full brightness for the whole ~5s cold fetch); UX wanted
  dimming REMOVED (at `opacity:.5` metadata contrast falls to 2.84:1, unreadable
  in morning sun). Resolution: take QA's timing and UX's treatment — fire the
  signal before the fetch, but as a full-opacity inset rail instead of dimming.
  `#hdrEta` is a sibling of `#content` and escaped the old treatment entirely, so
  it is covered now and is no longer permanently `--live` green.
- [shipped, after approval] All UX findings: `.mins` urgency colour, `sched` tag +
  rail on inbound schedule-only rows, "no live bus" replacing "none soon" for the
  dropout case, gate columns held 2 polls to stop layout shift, `.tab` to 44px.
- [investigated, REFUTED] UX claimed `.mins` can render a raw clock string
  (`departure_text`) at 28px and be misread as minutes. Checked against 83 live
  predictions: zero reach that branch. `njtCountdown()` falls back to `countdown`
  when `raw_countdown` is null, and the proxy always sends a numeric `countdown`,
  so the 08:40 AM bus renders "45 min", not "08:40". Dead code in practice — the
  finding was read out of the source and doesn't survive the data.
- [decided: LEAVE, Jeff 2026-07-30] That check did surface a real asymmetry:
  rows backed by an NJT prediction show the raw number plus "runs ~5 late", while
  pure-timetable rows (no `raw_countdown`) show the plain scheduled minutes with
  no correction and no note — verified at 07:54:43 against the scheduled times
  (predicted rows +5, timetable rows +0). Two rows on one card, one warning you
  and one not. Left alone deliberately: the fix is proxy-side (the client cannot
  compute the bias without `raw_countdown`), it is invisible unless the opt-in
  "Bus Predict Delays" toggle is on, and applying a prediction-drift constant to
  a timetable would assert a correction nobody has measured.

**The ONE thing this round:** the launcher tile was polling the proxy forever in
the background because the page ignored the `hidden` message it was already
being sent — now fixed and measured.

**Traps hit while shipping (worth not re-learning):**
- A snapshot repaint was collapsing the gate layout the gate-hold fix existed to
  stabilise. Held gates must be RENDERED on every paint but only AGED by a live
  one. Caught by a test, not by reading.
- `header >Cache-Control "no-cache"` in Caddy passes `caddy validate` and then
  silently drops the header, leaving the page cacheable for 10 minutes. Replacing
  an upstream response header needs `header_down` inside the `reverse_proxy`
  block; a plain `header` directive appends, which is how the origin came to emit
  two conflicting `Cache-Control` values.
- Headless Chromium cannot verify service-worker behaviour here (the in-page
  probe never resolves under `--virtual-time-budget`). Drive the SW's fetch
  handler from Node against a fake Cache API instead.

**What this round chose NOT to cover** (to inform future rounds): security and
the proxy's auth/CORS posture; cost/quota headroom on Cloud Run; accessibility
beyond contrast and tap-target size; the ferry board specifically; the
`/srv/launcher` shell's own code quality; anything about the wall dashboard or
the other tiles sharing that origin.
